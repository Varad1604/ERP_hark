SutraERP --- Architecture & Workflow Context Baseline

Document Status: Architecture Context Baseline
Date: 2026-07-05
Purpose: Preserve the agreed architectural, institutional, team-boundary, tiering, and workflow context before beginning Level 1 Institute Lifecycle design.

1. Product Definition

SutraERP is a modular institutional ERP and operating platform intended primarily for colleges and schools.

The product must support:

  • One institute containing one or more colleges.
  • One institute containing schools and colleges simultaneously.
  • Future multi-tenant SaaS deployment for completely separate institutes.
  • Multiple colleges/schools under the same institute with independent policies and operating structures.
  • Modules that can be added, disabled, or removed without crashing unrelated institutional functions.
  • Separate development teams working on different ERP domains.
  • Hybrid synchronous contracts and domain-event communication.
  • Institution-wide auditability.
  • Configurable approval workflows.
  • A canonical person and identity model.
  • Complete student lifecycle ownership.
  • University-affiliated colleges, autonomous colleges, and universities.
  • Parent/guardian access as a first-class ERP persona.
  • Institutional document management rather than generic file storage.

SutraERP is to be treated as an Institution Operating Platform, not a collection of CRUD pages.

2. Confirmed Institutional Scope

2.1 Tenant and Institution Model

Initial operating model:

flowchart TD
    A[SutraERP SaaS Platform] --> B[Tenant / Institute]
    B --> C[One or More Colleges and/or Schools]
    C --> D[Campuses / Organisational Units]

A single tenant may contain both schools and colleges simultaneously.

The architecture must therefore support different academic models within the same institute:

flowchart TD
    subgraph School Model
        S1[Class] --> S2[Division / Section] --> S3[Subject]
    end
    subgraph College Model
        C1[Programme] --> C2[Programme Version] --> C3[Batch / Cohort] --> C4[Semester / Term] --> C5[Course Offering]
    end

The platform must not force the school academic model into the college model or vice versa.

2.2 Independent College/School Policies

Different colleges or schools under the same institute may have different:

  • Academic calendars.
  • Academic years or operating periods.
  • Examination rules.
  • Fee policies.
  • Approval workflows.
  • Working calendars.
  • Institutional policies.

Therefore, configuration must support scope inheritance and local override.

Conceptually:

Platform Default
      ↓
Institute Policy
      ↓
College / School Policy
      ↓
Department / Organisational Unit Policy
      ↓
Workflow-Specific Override

A lower scope may override a higher-level policy only where the policy definition permits it.

2.3 Multiple Shifts

Multiple shifts are a valid institutional requirement.

Examples:

  • Morning Shift.
  • Evening Shift.
  • Polytechnic Shift.
  • Weekend Shift.
  • Special Programme Shift.

Shift capability is not required in the immediate core workflow implementation and may be introduced as an additional capability/module.

However, core identifiers and scheduling concepts should avoid assumptions that an institute has only one daily operating window.

2.4 Academic Year Approval

Initial default workflow:

Registrar
   ↓ Creates Academic Year / Academic Operating Period
DRAFT
   ↓ Submits
Principal
   ↓ Reviews
APPROVED
   ↓
Academic Year becomes available for operational setup

This is the initial business default.

The long-term architecture must allow this approval chain to be configurable through the central Workflow Engine.

The workflow must not permanently hardcode Registrar → Principal in domain service logic.

2.5 Guided Institute Setup

A guided Institute Setup workflow/wizard is approved as a future capability.

It is not a current Level 1 dependency.

The future wizard should orchestrate existing configuration capabilities rather than own a separate setup data model.

3. Current Repository Architecture

The audited repository is currently an Early Modular ERP implemented as a Modular Rust Monolith.

Current stack

  • Backend: Rust.
  • Web framework: Axum 0.7.
  • Async runtime: Tokio.
  • Database: PostgreSQL 16.
  • Database access: SQLx raw asynchronous SQL.
  • Pooling: PgBouncer.
  • Cache/support infrastructure: Redis.
  • Frontend: React 19.
  • Build tool: Vite.
  • Language: TypeScript.
  • Frontend state: Zustand for authentication.
  • HTTP client: Axios.
  • File infrastructure declared: MinIO, but complete Rust S3 integration is not confirmed.
  • Authentication: JWT HS256 with refresh tokens and Argon2id password hashing.
  • Authorization: mixed database-backed RBAC and hardcoded role-name checks.

Current backend model

One Rust Binary
      ↓
Axum Router
      ↓
Internal Domain Modules
      ↓
Shared AppState
      ↓
Single PostgreSQL Database

Current backend modules include:

  • Auth.
  • Student.
  • Academics.
  • Examination.
  • Finance.
  • Library.
  • Hostel.
  • Transport.
  • Placement.
  • Medical.
  • HR.
  • Health.

The current database uses one PostgreSQL database and one public schema with logical domain separation.

Architecture decision

SutraERP will not be redesigned as microservices at this stage.

The current modular monolith will evolve into a:

Contract-Driven Modular ERP Platform

Reasons:

  • Current scale does not justify distributed-service operational complexity.
  • Separate teams can be supported using domain ownership and explicit contracts.
  • A modular monolith permits transactional consistency where appropriate.
  • Future extraction into services remains possible if domain boundaries are disciplined.

Risk:

  • Without enforcement, developers may continue using direct cross-domain SQL and shared files, creating a distributed-monolith style coupling inside one binary.

13. Hybrid Communication Architecture

Agreed architecture:

COMMAND / QUERY
→ Synchronous Contract

DOMAIN FACT
→ Domain Event

Use synchronous contracts when an immediate authoritative answer or state change is required.

Example:

Examination asks:
"Is this student academically eligible for this examination?"

This requires an authoritative synchronous contract.

Use domain events to communicate facts that already occurred.

Example:

AdmissionApproved.v1
StudentActivated.v1
AttendanceFinalized.v1
LeaveApproved.v1

Transaction Flow

Business Transaction
↓
Domain Service
↓
Validation
↓
Authorization
↓
State Transition
↓
Database Commit
↓
Transactional Outbox Record
↓
Event Delivery
↓
Subscribers

The current in-memory Tokio broadcast channel is not sufficient for critical ERP workflow consistency because it has no transactional outbox, durable retry, or dead-letter handling.

It may remain for non-critical internal signalling during transition, but critical cross-domain workflows must not depend solely on ephemeral events.

14. Module Ownership Rules

Non-Negotiable Domain Rule

A module may read another domain only through an approved read contract.

A module may never write another domain's owned table directly.

Cross-domain state changes occur through:

  1. Command Contract.
  2. Domain Event.

Event Subscriber Rule

A subscriber must call the owning domain's service/command logic.

It must not directly insert/update another domain's tables.

Incorrect:

Hostel Event Subscriber
↓
INSERT INTO finance.fee_allocations

Correct:

HostelChargeAssessed.v1
↓
Finance Subscriber
↓
Finance Domain Service
↓
create_receivable()
↓
Finance-owned tables

17. Module Degradation Principle

Optional operational modules must fail independently where possible.

Example:

Hostel unavailable

Student admission       → Works
Student fee payment     → Works
Attendance              → Works
Examination             → Works
Hostel room allocation  → Unavailable

Example:

Notifications unavailable

Leave approval          → Completes
Domain state            → Committed
Notification delivery   → Pending / retried

An optional subscriber failure must not roll back an already committed authoritative domain transaction.

Critical exceptions are Tier 0/platform dependencies and explicitly declared mandatory domain preconditions.

  • Security owns security operations.

21. Known Current Architecture Risks

The repository audit identified the following major risks:

  1. In-memory event bus with no outbox; critical events may be lost on process crash.
  2. Monolithic DomainEvent enum creates cross-team edit and recompile coupling.
  3. Audit coverage is incomplete for major mutations.
  4. Team 1 has critical direct schema dependencies on Team 2-owned entities.
  5. Global RBAC path mapping can allow unmatched routes to bypass resource authorization.
  6. No configurable workflow engine exists.
  7. Academic Year and Semester are represented as duplicated primitive values rather than canonical entities.
  8. No complete Employee entity exists.
  9. Identity duplication remains possible.
  10. Class enrollment API is incomplete/missing.
  11. Attendance-to-examination eligibility is not wired.
  12. Faculty onboarding API is incomplete/missing.
  13. Most defined domain events have no consumer.
  14. Leave approval is not connected to attendance/payroll workflows.
  15. Multi-tenant provisioning is incomplete.

These risks must inform workflow design. They do not require an immediate microservice rewrite.

24. Decisions Locked Before Level 1

The following decisions are accepted as the baseline:

  1. SutraERP supports one institute with one or more colleges.
  2. Architecture should be future multi-tenant SaaS ready.
  3. One institute may contain schools and colleges simultaneously.
  4. Colleges/schools may use different academic calendars, examination rules, fee policies, and approval workflows.
  5. Multiple shifts are valid and may be introduced as an additional capability.
  6. Default Academic Year workflow is Registrar creates/submits and Principal approves.
  7. The approval architecture must remain configurable.
  8. Guided Institute Setup is a future capability and is not a current Level 1 dependency.
  9. SutraERP owns the complete student lifecycle.
  10. SutraERP supports affiliated, autonomous, and university examination contexts.
  11. Parent/guardian is a first-class ERP persona.
  12. Documents are institutional records, not generic cloud-drive files.
  13. Architecture remains a modular Rust monolith at this stage.
  14. Communication architecture is hybrid: synchronous contracts plus domain events.
  15. Modules are classified by architectural tiers, separate from P0/P1/P2 development priority.
  16. Person is canonical and may hold multiple personas.
  17. Outsourced security and cleaning workers use workforce engagements and are not automatically institute employees.
  18. Organisation Position and System Role are separate concepts.
  19. Team 1 owns Finance and Examination.
  20. Team 2 owns the broader platform and remaining domains.
  21. Cross-domain writes are prohibited.
  22. Cross-domain operational reads use approved read contracts.
  23. Dashboard is a composition surface.
  24. Reports do not own operational source data.
  25. Directory does not own Person.
  26. Lab Management is added to Tier 2.
  27. Lab In-charge is modelled as a position/assignment within Lab Management and workforce context.
  28. Infrastructure Management is added to Tier 2.
  29. Infrastructure Management is distinct from Facilities.
  30. Physical spaces require canonical identity and are referenced by operational modules.
